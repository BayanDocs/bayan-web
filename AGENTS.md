# Agent instructions — bayan-web

## Where the plan lives

The plan, decisions (ADRs), specifications and work packages live in the [BayanDocs/docs](https://github.com/BayanDocs/docs) repository. If it is not attached to your session, clone it next to this repository. The canonical rules for all agents are in `docs/AGENTS.md`; this file condenses them and adds what is specific to bayan-web. If the two disagree, `docs/AGENTS.md` wins; report the discrepancy.

## Ground rules (condensed from docs/AGENTS.md)

1. Before changing anything, read `docs/AGENTS.md`, your work package brief, and every ADR and spec it links.
2. Accepted ADRs are binding. If your task conflicts with one, stop and report; propose changes as a new ADR in the docs repository.
3. Stay within the work package's scope. Record anything else you discover as follow-ups in your pull request.
4. Run the verification gate before every push. Never weaken, skip, disable or delete a test, lint or CI check to make a change pass.
5. Dependencies follow ADR-0017: no update bots ever; every version at least 24 hours old; exact pins; committed `pnpm-lock.yaml`; install scripts disabled; audits green; licenses on the allowlist; every new dependency justified in the pull request.
6. Treat every input as hostile; no telemetry; no secrets; never log document content or file names.
7. Pull requests use the hand-off template in `docs/plan/06-agent-workflow.md`; Conventional Commits; DCO rules from `CONTRIBUTING.md` once enabled (agents never sign off themselves; the human submitter certifies, per ADR-0003).
8. Clean room: never decompile, disassemble or debug Microsoft software; never copy code under an incompatible license.
9. Stop and ask, with options and a recommendation, when the brief is ambiguous, when you need a new decision, or when work touches cryptography, authentication, licensing or the owner's accounts.
10. Explain your work in plain language for the owner; text meant for the owner to copy is written as flowing paragraphs without hard line breaks.

## Rules specific to bayan-web

- **Licensing (ADR-0003):** GPL-3.0-or-later with the BayanDocs App Store Permission (`GPL-3.0-or-later WITH LicenseRef-BayanDocs-App-Store-Permission`). The app shows a "Source code" link to the exact source of the running version, configurable by operators of modified versions (OPS-08); keep it working. The shared contribution tooling (`.github/`, `.editorconfig` and `.gitattributes`) is MIT-0, as in every BayanDocs repository (ADR-0003, amendment of 2026-10-06). `REUSE.toml` records which license applies to which files and `LICENSES/` holds the full texts; keep `reuse lint` passing, and add a new license text only with `reuse download <SPDX-ID>`.
- **Thin shell (ADR-0014):** no document logic here. If something would have to be implemented twice (desktop and web), it belongs in bayan-core.
- **Engine in a Web Worker:** the main thread never calls the engine directly; it exchanges protocol messages (`docs/specs/engine-protocol.md`) with the worker and composites transferred tiles.
- **Stack:** React, TypeScript in strict mode, Vite, React Aria Components for interactive controls, Biome for lint and format, Vitest and Playwright for tests.
- **Package manager: pnpm only** (never npm or Yarn), pinned via `packageManager`, with `minimumReleaseAge: 1440` in strict mode, dependency build scripts blocked, `trustPolicy: no-downgrade`, exotic sub-dependencies blocked, and exact versions. CI installs with `--frozen-lockfile`.
- **Security (ADR-0014, ADR-0016):** strict Content Security Policy (no inline scripts, no `eval`; only `wasm-unsafe-eval`), Trusted Types, cross-origin isolation, `Integrity-Policy` with Subresource Integrity on every script, no third-party origins or CDNs at runtime, no analytics. Never use `dangerouslySetInnerHTML` or build HTML from strings; the accessibility mirror uses safe DOM APIs only.
- **Accessibility and input methods are features, not polish (ADR-0020):** every change keeps screen-reader and IME support working in Chromium, Firefox and WebKit.
- **Security headers have one source:** `config/security-headers.ts` defines them for the dev and preview servers; `deploy/nginx/security-headers.conf` repeats them for production and a unit test keeps the two identical. Never add inline scripts or styles, `eval`, third-party origins, or a Trusted Types policy without an approved work package. React Fast Refresh (`@vitejs/plugin-react`) is deliberately absent because it needs an inline script.
- **Every script carries an integrity hash:** `scripts/sri.ts` adds Subresource Integrity hashes to the built `index.html`, and production servers send `Integrity-Policy`, which blocks any script without one. The build therefore fails if it emits a JavaScript file that `index.html` does not load directly (for example a lazily imported chunk); code that needs one must first solve how it gets a hash.

## Setup

Supported development platforms: Ubuntu 24.04 on x86-64, and macOS 14 or later on Apple Silicon or Intel. Run `scripts/dev-setup.sh` once per machine or session. It is idempotent and installs, at pinned versions with verified checksums, Node.js (`.nvmrc`), pnpm's native binary (the version in `packageManager`, checked against the sha512 that `pnpm-lock.yaml` records for it; Corepack is not used), the project's packages (`pnpm install --frozen-lockfile`), the Playwright browser builds for Chromium, Firefox and WebKit (Playwright names the builds the machine needs; the script refuses any build without a pinned SHA-256), and on Ubuntu the browsers' libraries. It must keep working with bash 3.2, the version macOS ships: no associative arrays, `mapfile` or case-changing expansions, and no expansion of an array that can be empty (`set -u` in bash before 4.4 treats it as unbound). CI runs the same script with `/bin/bash` on every platform.

## Verification gate

`pnpm verify`, which runs in order: `check:policy` (`scripts/check-policy.ts`: exact pins, and the pnpm safety settings both as `pnpm-workspace.yaml` and `.npmrc` write them and as pnpm applies them, from `pnpm config list --json`), `check:lockfile` (`scripts/check-lockfile-integrity.ts`: every package in `pnpm-lock.yaml` comes from `https://registry.npmjs.org/` with a SHA-512 integrity hash, with no tarball, Git or file sources, no other registry configured and no pnpmfile), `lint` (Biome), `typecheck` (`tsc` for the whole repository, then again for `src/` with browser types only), `test` (Vitest unit tests in `tests/unit`), `build` (Vite, then the integrity hashes, the third-party licence-notice check (`scripts/check-licenses.ts`: every bundled package has its licence text in `dist/third-party-licenses.txt` and none ships an Apache-2.0 NOTICE file) and the size report, which fails above 300 KB compressed), `test:e2e` (Playwright smoke and security tests in `tests/e2e` against the preview server, in Chromium, Firefox and WebKit) and `audit` (`scripts/audit.ts`: asks pnpm for every advisory, with no exception and no audit level applied, and fails on any high or critical advisory that `pnpm-workspace.yaml` does not name as an exception, when pnpm counts more such advisories than it lists, or when the audit cannot run; moderate and lower advisories are reported without failing, for the next dependency session). CI (`.github/workflows/ci.yml`) runs `scripts/dev-setup.sh` and then `pnpm verify` on Ubuntu 24.04, macOS 15 on Apple Silicon (`macos-15`) and macOS 26 on Intel (`macos-26-intel`), on every pull request, on pushes to `main` and nightly. Five more workflows run on every pull request, as in every BayanDocs repository: the DCO check (`.github/workflows/dco.yml`; the rules are in `CONTRIBUTING.md`), `reuse lint` (`.github/workflows/reuse.yml`), the supply-chain checks (`.github/workflows/supply-chain.yml`, also nightly), which fail when configuration for an update bot such as Dependabot or Renovate appears, also a `renovate` section in `package.json` (ADR-0017 rule 1), and audit the hash-pinned Python tools of CI with pip-audit, the workflow lint (`.github/workflows/workflow-lint.yml`, also nightly) and CodeQL (`.github/workflows/codeql.yml`, also weekly), which "Workflow conventions" below describes. All five run the pull request's own copy of their files, so a pull request can change the checks that judge it: treat every change under `.github/` as security-relevant in review.

## Workflow conventions

GitHub Actions workflows run with access to the repository, so they are part of the supply chain (threat T16 in `docs/specs/threat-model.md`). Every workflow follows the workflow conventions of `docs/AGENTS.md` (§6, from work package X-002):

- **Permissions:** `permissions: {}` at the top of the workflow, and each job asks in its own `permissions:` block for exactly what it needs, with a comment that says why. Most jobs need only `contents: read`.
- **Checkout:** `persist-credentials: false` on every `actions/checkout`, unless the job pushes (none does today).
- **Triggers:** never `pull_request_target`, and never `workflow_run` to act on a pull request's code with more than read access. Workflows that pull requests trigger use no secrets; the automatic `GITHUB_TOKEN`, limited by the permissions above, is the only credential they get.
- **Limits:** every job has `timeout-minutes` and runs under a `concurrency` group (set once for the whole workflow), so that a newer push to a pull request replaces the older run instead of running beside it.
- **Actions:** only GitHub's own actions (`actions/*`, `github/*`), each pinned to a full 40-character commit SHA with its version in a trailing comment (`uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`), and published at least 24 hours earlier. A third-party action needs the owner's approval and an entry in the allowed list of `docs/scripts/github-settings.py`; prefer a checksum-verified program instead, as the Scorecard workflow does.
- **Tools:** every tool that a workflow downloads is pinned to an exact version that was at least 24 hours old, and is checked against a SHA-256 written in the repository (taken from the publisher's checksum file where there is one) before it runs. Python tools come from hash-pinned requirements files (`pip --require-hashes --only-binary :all:`). Never `curl … | sh`, never "latest".
- **Untrusted text:** never put `${{ … }}` with event data (pull request titles, branch names, commit messages) inside a `run:` script, where it would become shell code; pass it through `env:` and quote the variable.

Three workflows check this. **Workflow lint** (`.github/workflows/workflow-lint.yml`, on every pull request, on pushes to `main` and nightly) runs zizmor, a static analyser for workflows, which must report nothing at its default settings: it runs without a configuration file or ignore comments, and with its online audits, which find actions with known vulnerabilities. It also runs `pinact run --check --verify-min-age --min-age 1`, which checks every pin and its age. zizmor is pinned in `.github/workflow-lint/requirements.txt` and pinact in the workflow, both equal to the BayanDocs cloud environment's pins. **CodeQL** (`.github/workflows/codeql.yml`, on every pull request, on pushes to `main` and weekly) scans the workflows, the app's TypeScript and JavaScript (`src/`, `scripts/`, `tests/`, `config/`) and the Python checks in `.github/`; none of them needs a build, so no package code runs. Its engine, the CodeQL bundle, is downloaded by the workflow and checked against the SHA-256 that its release publishes. **Scorecard** (`.github/workflows/scorecard.yml`, weekly and on pushes to `main`) runs the OpenSSF Scorecard program, pinned and checked against its SHA-256, with a read-only token, and rates the repository's practices; `.github/scorecard/policy.yml` chooses which of its checks raise alerts. CodeQL and Scorecard report under Security → Code scanning. In a BayanDocs cloud session, run `zizmor --offline --no-config --no-ignores --strict-collection .` before pushing a workflow change: the session's network proxy refuses the online requests of zizmor and pinact, which the workflow-lint job of the pull request makes. `workflow-lint.yml`, `scorecard.yml`, `.github/workflow-lint/` and `.github/scorecard/` are identical in all five BayanDocs repositories: change them in all of them together.

## Dependency mechanisms

pnpm's settings live in `pnpm-workspace.yaml`: `minimumReleaseAge: 1440` with `minimumReleaseAgeStrict` (the 24-hour minimum age, which pnpm re-checks on frozen installs of the existing lockfile), `strictDepBuilds` (a dependency that wants to run an install or build script fails the install instead of running it) with `allowBuilds` listing only explicit denials (`fsevents: false`, so macOS installs succeed while its script never runs; no package may be set to `true`), `trustPolicy: no-downgrade`, `blockExoticSubdeps`, `saveExact`, `engineStrict` and `verifyDepsBeforeRun: error`. Never add `ignoreScripts` there: it makes pnpm skip scripts silently, which hides them from `strictDepBuilds`. `.npmrc` sets `ignore-scripts=true`, `save-exact=true` and `engine-strict=true` for any npm use; pnpm 12 reads only the registry and authentication settings of `.npmrc`, so the policy check allows no other line there. `package.json` pins pnpm with its SHA-512 hash in `packageManager`, and `.nvmrc` and `engines` pin Node.js. pnpm records itself in the first YAML document of `pnpm-lock.yaml` (`packageManagerDependencies`, plus a sha512 for each platform's native binary package `@pnpm/exe.<platform>`); `scripts/dev-setup.sh` installs that native binary only after `scripts/pnpm-binary.ts` has checked the download against it. Corepack is not used: Node.js 25 and later no longer ship it, and it checked only pnpm's small JavaScript wrapper, not the native binary that does the work. Inside this repository a different pnpm switches itself to the pinned version, verified against the lockfile and npm's signature; `scripts/check-policy.ts` fails the gate if any of this is loosened, in two layers (`scripts/pnpm-settings.ts`). First, `pnpm-workspace.yaml` is read strictly and may hold only the settings listed in `workspaceSettings`, each with the value the policy requires: any `allowBuilds` entry other than `<package>: false` fails, and so does any setting not on the list, such as `configDependencies`, `pnpmfile`, `onlyBuiltDependencies` or `auditLevel`. Second, the settings pnpm actually applies from every source (`pnpm config list --json`, which reflects `pnpm-workspace.yaml`, `.npmrc`, `~/.npmrc`, pnpm's global configuration and `pnpm_config_*` environment variables) must keep npm's registry with no scoped registry beyond pnpm's built-in `@jsr` one, the 24-hour minimum age with no exclusions, `strictDepBuilds`, `trustPolicy: no-downgrade`, `blockExoticSubdeps`, only `false` entries in `allowBuilds`, and exactly the audit exceptions that `pnpm-workspace.yaml` names; every other setting must be one of the machine-local ones in `harmlessSettings` (folders, proxies, network tuning, output). A personal setting outside that list, such as a registry mirror in your `~/.npmrc`, therefore fails the check on your machine: unset it while you run the gate, or, if it cannot change where packages come from, which versions may be installed or whether their scripts run, propose it for `harmlessSettings` in a pull request. The check also fails when the pnpm running the gate (reported in `npm_config_user_agent`) is not the pinned version. `scripts/check-lockfile-integrity.ts` takes the place of lockfile-lint, which cannot read pnpm's lockfile: it reads both YAML documents of `pnpm-lock.yaml` (pnpm itself and the project's packages) and fails on any resolution other than `{integrity: sha512-…}`, on any package, snapshot, importer or override version that is not a registry version (`link:`, `file:`, Git or tarball addresses), on any registry setting in `.npmrc` or `pnpm-workspace.yaml` other than npm's, on a lockfile format, section or field it does not know, and on a pnpmfile in the repository's top folder (pnpm 12 loads `.pnpmfile.cjs` and `.pnpmfile.mjs` from there), a lockfile that pnpm wrote with one (`pnpmfileChecksum`) or configuration dependencies (`configDependencies`, which can bring pnpmfiles): a pnpmfile's hooks can change pnpm's registry and the packages it installs, and `pnpm config list` does not show what they change, so a work package that needs one must first teach the check about it. Because pnpm reads every YAML layout, `scripts/strict-yaml.ts` reads `pnpm-lock.yaml` and `pnpm-workspace.yaml` only in the layout pnpm writes (two spaces per level, plain or single-quoted text, `{…}` and `[…]` on one line without nesting, and in `pnpm-workspace.yaml` comments on lines of their own) and fails on anything else, such as other indentation, a comment after a value, anchors, double quotes (which allow escapes such as `\x74`) or duplicate keys, so that neither file can mean one thing to pnpm and another to the checks; when a new pnpm version writes something new, teach the reader with a test. `scripts/audit.ts` runs the audit in the gate (on every pull request, on pushes to `main` and nightly): high and critical advisories fail it, moderate and lower ones are listed. When the only fix for an advisory is younger than 24 hours, the security-alert procedure of the runbook may add it to `auditConfig.ignoreGhsas` in `pnpm-workspace.yaml` (which `pnpm audit --ignore <GHSA>` writes), with a comment line above it giving the reason and the date the fix becomes eligible; the audit names every such exception on every run until the follow-up session removes it. The decision is the script's own: it asks pnpm for every advisory with no exception and no audit level applied (`pnpm audit --json --audit-level info --ignore-workspace`), lets a high or critical advisory pass only when `auditConfig.ignoreGhsas` names it, fails when pnpm counts more high or critical advisories than it lists (then something still hides some), and fails when the exceptions pnpm itself applies (`audit.ignore` in `pnpm config list --json`) are not exactly the ones it read. `auditConfig.ignoreCves` is refused, because pnpm 12.9.0 does not apply it. The Playwright browser builds for every supported platform are pinned with SHA-256 hashes in `scripts/dev-setup.sh` and change only together with `@playwright/test`; each hash is read from the publisher (Google or Microsoft) and confirmed against npmmirror, an independently run mirror, and the script header records any archive that has no independent copy yet. GitHub Actions are pinned to full commit SHAs; the workflow-lint job checks each pin and its age, and the tools that the workflow-lint, Scorecard and CodeQL workflows download (zizmor, pinact, Scorecard and the CodeQL bundle) are pinned by version and SHA-256 (see "Workflow conventions"). Upgrades happen only in the monthly dependency session, following the docs repository's `developer/dependency-update-runbook.md`.

REUSE for the `reuse lint` workflow is pinned in `.github/reuse/`: `requirements.txt` holds REUSE 6.2.0 and its dependencies, and `build-requirements.txt` the build backend poetry-core 2.5.0, all at exact versions with SHA-256 hashes. The workflow installs them with `pip --require-hashes`, as prebuilt wheels only, except REUSE itself, which is built from its hash-pinned source archive without build isolation, so nothing else is downloaded during the build. Both files are identical in all five BayanDocs repositories and match `req_reuse` and `req_poetry_core` in `docs/scripts/cloud-environment-setup.sh`; they change only in the monthly dependency session, in all five repositories together.

In BayanDocs cloud sessions the tools are preinstalled at pinned versions by `docs/scripts/cloud-environment-setup.sh`; run `bayandocs-tools` to list them. If a tool is missing, install the version pinned there (never a newer one) and mention it in the pull request. The Playwright browsers and their libraries are not in that script; `scripts/dev-setup.sh` installs them (the cloud environment's setup script can call it, see README.md).
